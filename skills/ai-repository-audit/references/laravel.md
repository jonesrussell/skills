# Laravel profile

Use this profile when the repository has an `artisan` file or a `composer.json` that requires `laravel/framework`. It adds Laravel defaults to the general audit. It does not replace the project's own rules: where the project documents a different convention, audit against that.

Confirm installed versions before judging an API or rule (`composer show --direct`, `composer show <vendor/package>`). PHP, Laravel, Pest and Larastan rules differ between major versions.

## Where the standards live

Look for the project's authority in this order, and record which sources you found:

- `AGENTS.md`, `CLAUDE.md` and similar agent files. These are often generated by Laravel Boost (`<laravel-boost-guidelines>` blocks, `=== foundation rules ===` headings). Generated text describes framework conventions, not decisions the project made. Treat it as background unless the project has edited or extended it.
- `.ai/rules/` (Boost's area-grouped rules; `index.md` maps globs to rule files) and other committed rule directories.
- ADRs, architecture or module docs, contributing guides and PR templates, in the repository or in a workspace the user names.
- Reviewer conventions: repeated review comments, a lead reviewer's stated preferences, or notes the user supplies. These are reviewer-enforced standards. Record where you learned them and do not present them as written policy.

A stock Laravel `README.md` (the framework's own "About Laravel" text) is not a project authority. Say so in the report rather than citing it.

If none of these define the rule you would audit against, report the gap as missing coverage instead of inventing a standard.

## Default guard-matrix rows

Start the guard matrix with these rows. For each, record what it scans, how it is selected and the observed outcome, as the general skill requires.

| Guard | Where to look | What to check |
|-------|---------------|---------------|
| Pint | `pint.json`, composer scripts, CI | Whether CI runs `pint --test` (a check) or `pint` (a rewrite that never fails). Preset and excluded paths. |
| Larastan / PHPStan | `phpstan.neon` or `phpstan.neon.dist`, `phpstan-baseline.neon` | Level and `paths` (often only `app/`). Baseline size and whether it grew since the audit baseline. `ignoreErrors` entries. |
| Pest arch tests | `tests/Arch*.php`, `tests/**/ArchTest.php` | Presets in use (`php`, `security`, `laravel`, `strict`). For each custom rule, the namespaces it actually targets and any `->ignoring()`. A rule over two controllers does not guard thirty. |
| Test selection | `phpunit.xml` | Which `<testsuite>` entries exist and which ones CI selects. Excluded groups, `<source>` include/exclude, test database settings. |
| Composer scripts | `composer.json` `scripts` | What `ci:check`, `test`, `lint` or similar actually run, and whether CI calls them or duplicates them. |
| CI triggers | `.github/workflows/*.yml` or other CI config | `on.push.branches` and `on.pull_request.branches` compared with the real default branch (`gh repo view --json defaultBranchRef` or `git symbolic-ref refs/remotes/origin/HEAD`). A trigger on `main` in a repository whose default branch is `0.1.x` selects nothing. |
| Deploy workflow | Vapor, Forge, Cloud, Envoyer or custom deploy jobs | The last run's result (`gh run list --workflow <file> --limit 3`). A failing or never-run deploy is a finding, even when tests pass. |
| Runtime PHP | `Dockerfile`, `vapor.yml` `runtime`, Cloud or Forge settings, `.tool-versions` | Runtime PHP compared with the CI matrix PHP and the `composer.json` `require.php` constraint and `config.platform.php`. CI on a newer PHP than production hides incompatibilities. |

Add the project's own guards (Rector, Psalm, PHP Insights, Deptrac, custom Artisan checks) when they exist.

## Laravel drift checks

Audit these where the project adopts them. Each is a common Laravel convention, not a universal rule; skip or adjust any that the project's authority rejects.

- **Thin controllers.** Controllers parse the request, call one action or service and return a response or resource. Look for queries, loops over models, transactions and side effects in controllers.
- **Validation in Form Requests.** Look for `$request->validate()`, `Validator::make()` or inline rule arrays in controllers, and Form Requests that exist but are not type-hinted.
- **Actions own the transaction.** If the project uses Action classes, check that the action opens `DB::transaction()` and that controllers, jobs and listeners do not wrap or split it. Look for nested or missing transactions around multi-write operations.
- **Audit and outbox inside the transaction.** Audit-log writes and outbox records belong in the same transaction as the change they describe. Direct dispatches of events, jobs or notifications from inside a transaction need `afterCommit` or an outbox.
- **Module boundaries.** For modular layouts (`app/Modules`, `Modules/`, `src/<Domain>`), search for imports of another module's internals and for cycles between modules. Shared contracts or events are the usual allowed path.
- **Hidden logic in observers and model events.** Check `Observer` classes, `booted()` hooks, `$dispatchesEvents` and global scopes for business logic that bypasses the action layer or makes writes depend on model lifecycle.
- **Migration folding.** If the project folds or squashes migrations before release, check that folded migrations match the current schema (`php artisan schema:dump` or a fresh migrate) and that no released migration was rewritten after deploy.
- **Backed enums.** Status and type columns should use backed enums with model casts rather than string or integer constants. Check for constants classes and raw string comparisons that duplicate an enum.

Confirm each finding against the code. A naming pattern match is a lead, not evidence.

## Cheap probes

To learn whether widening a guard would pass today, add a temporary Pest arch test, run only that file, record the result, then delete the file. For example:

```php
arch('controllers do not open transactions')
    ->expect('App\Http\Controllers')
    ->not->toUse('Illuminate\Support\Facades\DB');
```

Run it with `vendor/bin/pest path/to/TemporaryArchTest.php`. State in the report that the probe was temporary and removed, and check `git status` afterwards. A probe is evidence for a recommendation; it is not a guard until the owner adds it.

Arch tests inspect code statically and do not need a database, so they are safe to run first.

## Verification order

1. Static checks: `pint --test`, Larastan with the project's config, `composer validate`.
2. Arch tests and other database-free suites, selected by file or `--filter`.
3. The feature suite, only when its database is safe to use.

Feature suites often need a test database (MySQL, PostgreSQL) or one shared with another worktree, session or CI job. Do not reset, migrate or seed a shared database for an audit. Either record the feature suite as a coverage limit, or reuse the CI result for the PR merge ref and name the run you reused. SQLite in-memory results do not prove behaviour on the production database.

## Baseline convention

If the repository has no accepted audit to compare against, say so and treat this audit as provisional (see the general skill). When the owner accepts an audit with no open findings, recommend tagging that commit, for example `audit/YYYY-MM-DD`, and recording the tag in the audit report. The next run then uses the latest `audit/*` tag as its baseline. Do not create or push the tag yourself unless the user asks.
