# Roadmaps and requested delivery trackers

Use existing repository or editorial conventions. Distinguish implemented behaviour, current verification, user-reported results and stale records. Orientation does not itself authorize setup or implementation.

Derive milestones from the brief: foundation, complete product slices, MVP and public launch where applicable. Each milestone should identify the behaviour it proves, dependencies and observable exit evidence. Keep required capabilities inside MVP and mark proposed decisions explicitly. Estimate dates only when pace and uncertainty support them.

When requested, make a temporary delivery tracker a read-only HTML/CSS snapshot maintained beside the roadmap. Show the current milestone, next action, what exists, what is missing and meaningful release gates. Keep detailed task lists in their canonical source.

Inspect the application's design tokens before styling. Reuse its typography, palette and component conventions. Avoid external fonts or other network dependencies merely for presentation. Keep the tracker separate from product routes, data, credentials and paid services.

Label the snapshot date and evidence status. A dashboard does not promote a plan to verified completion. Avoid checklist percentages, forms, filters and local storage unless the user actually wants interactive task management.

Check desktop and narrow layouts through permitted browser tools when available. Report any visual verification limitation. Do not add a tracker to every bootstrap or turn a one-off presentation preference into a universal rule.
